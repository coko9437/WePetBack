    // src/pages/post/BoardPage.jsx
    useEffect(() => {
        const fetchPosts = async () => {
            try {
                // API로 보낼 파라미터 객체 생성
                const params = {
                    postType: (type || '').toUpperCase(), // 'missing' 또는 'shelter'

        };

**[Backend] ③ 동적 쿼리 생성 및 DB 조회 (QueryDSL)**

*   **파일**: `src/main/java/com/busanit501/findmyfet/repository/post/PostRepositoryCustomImpl.java`
*   **역할**: 서비스 계층으로부터 전달받은 검색 조건(criteria)을 바탕으로 QueryDSL을 사용하여 동적인 WHERE 절을 생성하고, 페이징 처리가 적용된 데이터를 데이터베이스에서 조회합니다.
*   **코드**:
    ```java
    // src/main/java/com/busanit501/findmyfet/repository/post/PostRepositoryCustomImpl.java
    @Override
    public Page<Post> search(FindPetSearchCriteria criteria, Pageable pageable) {
        QPost post = QPost.post;
        BooleanBuilder booleanBuilder = new BooleanBuilder(); // 동적 쿼리 생성을 위한 빌더

        // 게시판 타입(postType) 조건 추가
        if (StringUtils.hasText(criteria.getPostType())) {
            booleanBuilder.and(post.postType.eq(PostType.valueOf(criteria.getPostType().toUpperCase())));
        }
        // ... 다른 검색 조건들(제목, 지역 등) 추가 ...

        // QueryDSL을 사용한 쿼리 실행
        JPAQuery<Post> query = queryFactory.selectFrom(post)
                .where(booleanBuilder)
                .offset(pageable.getOffset()) // 페이징 처리: 시작 위치
                .limit(pageable.getPageSize())  // 페이징 처리: 가져올 개수
                .orderBy(post.createdAt.desc());

        List<Post> content = query.fetch(); // 쿼리 실행 및 결과 가져오기
        
        long total = countQuery.fetchOne(); // 전체 개수 카운트
        
        return new PageImpl<>(content, pageable, total); // 페이징 결과 객체로 반환
    }
    ```
*   **설명**: QueryDSL의 `BooleanBuilder`를 사용하여 `postType` 등 `criteria` 객체에 값이 있는 조건들만 동적으로 WHERE 절에 추가합니다. `pageable` 객체로부터 `offset`(페이지 시작점)과 `limit`(가져올 데이터 수) 정보를 얻어 페이징 쿼리를 완성합니다. 이렇게 조회된 데이터 목록(`content`)과 전체 데이터 수(`total`)를 `PageImpl` 객체에 담아 서비스 계층으로 반환합니다. 이 `PageImpl` 객체에는 현재 페이지 번호, 전체 페이지 수 등의 페이징 정보가 모두 포함되어 있습니다.

**[Frontend] FormData 생성 및 API 요청**

*   **파일**: `src/pages/post/PostFormPage.jsx`
*   **역할**: 사용자가 입력한 텍스트 데이터와 첨부한 이미지 파일들을 `FormData` 객체 하나에 담아 백엔드 API로 전송합니다.
*   **코드**:
    ```javascript
    // src/pages/post/PostFormPage.jsx
    const handleSubmit = async (e) => {
        e.preventDefault();
        
        // 텍스트와 파일을 함께 보내기 위한 FormData 객체 생성
        const apiFormData = new FormData();

        // 1. 사용자가 입력한 텍스트 정보들을 JSON 형태로 변환
        const requestDto = { ...formData, /* ... 데이터 가공 ... */ };

        // 2. JSON 데이터를 'requestDto'라는 이름의 파트(Part)로 추가
        apiFormData.append('requestDto',
            new Blob([JSON.stringify(requestDto)], { type: "application/json" }));

        // 3. 사용자가 첨부한 이미지 파일들을 'images'라는 이름의 파트로 추가
        newImageFiles.forEach(file => apiFormData.append('images', file));

        try {
            // ✅ 생성된 FormData를 API 함수에 담아 서버로 전송
            await createPost(apiFormData);
            alert('게시글이 성공적으로 등록되었습니다.');
            navigate(`/board/${formData.postType.toLowerCase()}`);
        } catch (err) { /* ... 에러 처리 ... */ }
    };
    ```
*   **설명**: `handleSubmit` 함수는 `FormData` 객체를 생성하여 멀티파트(Multipart) 요청을 준비합니다. 사용자가 입력한 폼의 텍스트 데이터는 `requestDto`라는 이름의 JSON 파트로, 첨부한 이미지 파일들은 `images`라는 이름의 파일 파트로 각각 `append` 합니다. 이렇게 두 종류의 데이터를 하나로 합친 `apiFormData`를 `createPost` API 함수를 통해 백엔드로 전송합니다.

**[Backend] 멀티파트 데이터 처리**

*   **파일**: `src/main/java/com/busanit501/findmyfet/controller/post/PostController.java`
*   **역할**: 프론트엔드에서 보낸 멀티파트 요청을 받아 JSON 데이터와 이미지 파일들을 각각 별개의 파라미터로 분리하여 서비스 계층에 전달합니다.
*   **코드**:
    ```java
    // src/main/java/com/busanit501/findmyfet/controller/post/PostController.java
    @PostMapping(consumes = {MediaType.APPLICATION_JSON_VALUE, MediaType.MULTIPART_FORM_DATA_VALUE})
    public ResponseEntity<String> createPost(
            @Valid @RequestPart("requestDto") PostCreateRequestDto requestDto,
            @RequestPart(value = "images", required = false) List<MultipartFile> images,
            @AuthenticationPrincipal UserDetailsImpl userDetails) {
        
        Long userId = userDetails.getUser().getUserId();
        Long postId = postService.createPost(requestDto, images, userId);

        return ResponseEntity.status(HttpStatus.CREATED).body("게시글 등록 완료. ID: " + postId);
    }
    ```
*   **설명**: `@PostMapping`의 `consumes` 속성을 통해 JSON과 멀티파트 데이터를 모두 처리할 수 있음을 명시합니다. `@RequestPart` 어노테이션을 사용하여 프론트에서 `append` 했던 파트 이름('requestDto', 'images')을 기준으로 JSON 데이터는 `PostCreateRequestDto` 객체로, 이미지 파일들은 `List<MultipartFile>`로 각각 정확하게 매핑하여 받습니다. 이렇게 분리된 데이터는 `postService`로 전달되어 실제 비즈니스 로직을 처리하게 됩니다.

### 5. 게시글 작성 결과 확인 (목록 썸네일)

*( 여기에 방금 작성한 게시글이 포함된 게시판 목록 캡처 이미지 삽입 )*

#### 5.2. 코드 리뷰

**[Backend] DTO 변환 시 썸네일 URL 생성**

*   **파일**: `src/main/java/com/busanit501/findmyfet/config/RootConfig.java` (ModelMapper 설정)
*   **역할**: `Post` 엔티티를 목록 조회용 DTO(`PostListResponseDto`)로 변환할 때, 엔티티에 연결된 여러 이미지 중 첫 번째 이미지의 URL을 썸네일 URL로 지정하는 규칙을 정의합니다.
*   **코드**:
    ```java
    // src/main/java/com/busanit501/findmyfet/config/RootConfig.java
    @Bean
    public ModelMapper getMapper() {
        ModelMapper modelMapper = new ModelMapper();
        // ... 다른 설정 생략 ...

        // Post -> PostListResponseDto 매핑 설정
        modelMapper.createTypeMap(Post.class, PostListResponseDto.class)
                .addMappings(mapper -> {
                    mapper.map(Post::getId, PostListResponseDto::setPostId);

                    // ✅ images 리스트에서 첫 번째 이미지 URL을 thumbnailUrl 필드에 매핑
                    mapper.using((Converter<List<Image>, String>) context ->
                            (context.getSource() == null || context.getSource().isEmpty()) ?
                                    null : context.getSource().get(0).getImageUrl()
                    ).map(Post::getImages, PostListResponseDto::setThumbnailUrl);
                    
                    // ... 작성자 정보 매핑 생략 ...
                });
        return modelMapper;
    }
    ```

*   **파일**: `src/main/java/com/busanit501/findmyfet/service/post/PostServiceImpl.java`
*   **역할**: 컨트롤러로부터 `postId`를 받아 데이터베이스에서 해당 `Post` 엔티티를 조회합니다. 이때, 연관된 `User`(작성자)와 `Image`(이미지 목록) 정보도 함께 조회하여 DTO로 변환 후 반환합니다.
*   **코드**:
    ```java
    // src/main/java/com/busanit501/findmyfet/service/post/PostServiceImpl.java
    @Override
    @Transactional(readOnly = true)
    public PostDetailResponseDto findPostById(Long postId) {
        // ✅ Post 조회 시 연관된 User와 Image도 함께 조회됨 (Fetch Join 또는 LAZY 로딩)
        Post post = postRepository.findById(postId)
                .orElseThrow(() -> new IllegalArgumentException("해당 게시글이 없습니다. id=" + postId));
        
        // ModelMapper를 사용하여 Post 엔티티를 PostDetailResponseDto로 변환
        PostDetailResponseDto responseDto = modelMapper.map(post, PostDetailResponseDto.class);

        return responseDto;
    }
    ```
*   **설명**: `postRepository.findById(postId)`를 통해 `Post` 엔티티를 조회합니다. JPA의 영속성 컨텍스트와 LAZY 로딩(또는 Fetch Join) 덕분에, 이후 `modelMapper`가 `post.getUser()`나 `post.getImages()`에 접근할 때 연관된 `User`와 `Image` 엔티티들이 자동으로 조회됩니다. `ModelMapper`는 `RootConfig`에 정의된 매핑 규칙에 따라 `Post` 엔티티와 그 연관 엔티티들의 정보를 `PostDetailResponseDto` 객체 하나에 모두 담아 컨트롤러로 반환하고, 이 DTO가 최종적으로 프론트엔드에 전달됩니다.

**[Backend] 게시글 수정 로직 처리**

*   **파일**: `src/main/java/com/busanit501/findmyfet/service/post/PostServiceImpl.java`
*   **역할**: 컨트롤러로부터 수정 데이터(DTO, 새 이미지 파일, `postId`, `userId`)를 받아, 권한을 검증하고, JPA의 더티 체킹(Dirty Checking)과 연관관계 관리를 통해 게시글을 효율적으로 업데이트합니다.
*   **코드**:
    ```java
    // src/main/java/com/busanit501/findmyfet/service/post/PostServiceImpl.java
    @Override
    @Transactional
    public void updatePost(Long postId, PostUpdateRequestDto requestDto, List<MultipartFile> newImages, Long userId) {
        Post post = postRepository.findById(postId).orElseThrow(/* ... 예외 ... */);
        validatePostAuthorOrAdmin(post, userId); // 1. 권한 검사

        // 2. 삭제 요청된 기존 이미지 처리
        if (requestDto.getDeletedImageIds() != null) {
            Set<Long> deleteIds = new HashSet<>(requestDto.getDeletedImageIds());
            Iterator<Image> iterator = post.getImages().iterator();
            while (iterator.hasNext()) {
                Image image = iterator.next();
                if (deleteIds.contains(image.getId())) {
                    fileUploadService.delete(image.getImageUrl()); // 실제 파일 삭제
                    iterator.remove(); // ✅ 컬렉션에서 제거 -> orphanRemoval=true로 DB에서도 삭제
                }
            }
        }

        // 3. 텍스트 정보 업데이트 (JPA 더티 체킹 활용)
        post.update(requestDto);

        // 4. 새로운 이미지 파일 추가
        if (newImages != null && !newImages.isEmpty()) {
            for (MultipartFile imageFile : newImages) {
                String storedFilename = fileUploadService.upload(imageFile);
                post.addImage(Image.builder().imageUrl(storedFilename).build());
            }
        }
        // ✅ @Transactional 덕분에 postRepository.save()를 호출할 필요 없음
    }
    ```
*   **설명**: 먼저 게시글 작성자 본인인지 권한을 확인합니다. DTO에 포함된 `deletedImageIds`를 이용해 `post` 엔티티의 `images` 컬렉션에서 해당 `Image` 객체를 제거합니다. `@OneToMany`에 `orphanRemoval=true` 옵션이 설정되어 있으므로, 컬렉션에서 제거된 `Image` 엔티티는 트랜잭션 종료 시 DB에서도 자동으로 삭제됩니다. `post.update(requestDto)`를 통해 엔티티의 텍스트 필드를 변경하면, `@Transactional` 환경의 더티 체킹(Dirty Checking) 기능이 이를 감지하여 별도의 `save` 호출 없이도 UPDATE 쿼리를 실행합니다. 마지막으로, 새로 첨부된 `newImages`를 파일 시스템에 저장하고 `Image` 엔티티로 만들어 `post`에 추가합니다.

**[Backend] 게시글 및 연관 데이터 삭제**

*   **파일**: `src/main/java/com/busanit501/findmyfet/service/post/PostServiceImpl.java`
*   **역할**: 컨트롤러로부터 `postId`와 `userId`를 받아 권한 검증 후, 해당 `Post` 엔티티와 연관된 모든 `Image` 엔티티 및 실제 이미지 파일들을 삭제합니다.
*   **코드**:
    ```java
    // src/main/java/com/busanit501/findmyfet/service/post/PostServiceImpl.java
    @Override
    @Transactional
    public void deletePost(Long postId,  Long userId) {
        Post post = postRepository.findById(postId).orElseThrow(/* ... 예외 ... */);
        validatePostAuthorOrAdmin(post, userId); // 권한 검사

        // 1. 연관된 이미지 파일들을 서버에서 삭제
        if (post.getImages() != null && !post.getImages().isEmpty()) {
            for (Image image : post.getImages()) {
                fileUploadService.delete(image.getImageUrl());
            }
        }

        // 2. Post 엔티티 삭제
        // ✅ cascade = CascadeType.ALL 설정 덕분에 Post를 삭제하면 Image도 함께 삭제됨
        postRepository.delete(post);
    }
    ```
*   **설명**: 먼저 권한을 확인한 후, `post` 엔티티에 연결된 `Image` 목록을 순회하며 `fileUploadService.delete`를 호출하여 서버에 저장된 실제 이미지 파일들을 먼저 삭제합니다. 그 후 `postRepository.delete(post)`를 호출하여 `Post` 엔티티를 삭제합니다. 이때, `Post` 엔티티의 `@OneToMany` 관계 설정에 `cascade = CascadeType.ALL` 옵션이 지정되어 있으므로, 부모인 `Post`가 삭제될 때 자식인 `Image` 엔티티들도 데이터베이스에서 연쇄적으로 함께 삭제됩니다.

### 9 & 10. '찾기 완료' 상태 변경 및 결과 확인

#### 9.1. 사용자 시나리오
상세 조회 화면에서 '찾았어요!' 버튼을 누르면 상태 변경 확인창이 뜹니다. '확인'을 누르면 버튼들이 사라지고, 게시글 상단에 있던 '찾는 중' 뱃지가 '찾았어요!' 뱃지로 변경됩니다. 이후 목록으로 돌아가면 해당 게시글 카드의 뱃지 또한 '가족 찾음!'으로 변경된 것을 확인할 수 있습니다.

*( 여기에 '찾았어요!' 버튼 클릭 후 상태 뱃지가 변경된 상세 페이지와, 목록 페이지의 카드 캡처 이미지를 나란히 삽입 )*

#### 10.2. 코드 리뷰

**[Frontend] 상태 변경 요청 및 UI 갱신**

*   **파일**: `src/pages/post/PostDetailPage.jsx`
*   **역할**: '찾았어요!' 버튼 클릭 시 `completePost` API를 호출하고, 성공 시 서버로부터 최신 게시글 데이터를 다시 받아와 화면을 갱신합니다.
*   **코드**:
    ```javascript
    // src/pages/post/PostDetailPage.jsx
    const handleComplete = async () => {
        if (window.confirm("... 상태를 변경하시겠습니까?")) {
            try {
                await completePost(postId); // 상태 변경 API 호출
                alert("처리가 완료되었습니다.");
                fetchPost(); // ✅ 상태 변경 후, 최신 데이터를 다시 불러와 화면을 갱신
            } catch (err) {
                alert('상태 변경에 실패했습니다.');
            }
        }
    };

    // ... 렌더링 부분 ...
    const isCompleted = post.status === 'COMPLETED';
    const statusText = isCompleted ? '찾았어요!' : '찾는 중';
    
    return (
        // ... 생략 ...
        <div className={`status-badge ${isCompleted ? 'status-completed' : 'status-active'}`}>
            {statusText}
        </div>
        {isAuthor && !isCompleted && ( // ✅ 완료되지 않았을 때만 버튼 노출
            <div className="post-actions">
                {/* ... 버튼들 ... */}
            </div>
        )}
    )
    ```*   **설명**: `handleComplete` 함수는 `completePost` API를 호출하여 백엔드에 상태 변경을 요청합니다. 요청이 성공하면, `fetchPost` 함수를 다시 호출하여 서버로부터 변경된 `status` 값이 포함된 최신 게시글 데이터를 가져옵니다. 이 데이터로 `post` 상태가 업데이트되면 React가 컴포넌트를 리렌더링하면서, `isCompleted` 변수 값이 `true`로 바뀌고, 이에 따라 '찾았어요!' 뱃지가 표시되고 수정/삭제 버튼들은 사라지게 됩니다.

**[Backend] 게시글 상태 변경 로직**

*   **파일**: `src/main/java/com/busanit501/findmyfet/service/post/PostServiceImpl.java`
*   **역할**: 컨트롤러로부터 `postId`와 `userId`를 받아 권한 검증 후, 해당 `Post` 엔티티의 상태를 'COMPLETED'로 변경합니다.
*   **코드**:
    ```java
    // src/main/java/com/busanit501/findmyfet/domain/post/Post.java
    public void complete() {
        this.status = Status.COMPLETED; // 상태를 COMPLETED로 변경하는 메서드
    }

    // src/main/java/com/busanit501/findmyfet/service/post/PostServiceImpl.java
    @Override
    @Transactional
    public void completePost(Long postId, Long userId) {
        Post post = postRepository.findById(postId).orElseThrow(/* ... 예외 ... */);
        validatePostAuthorOrAdmin(post, userId); // 권한 검사

        // ✅ 엔티티의 상태 변경 메서드 호출
        post.complete();

        // ✅ @Transactional에 의해 더티 체킹이 일어나고, 자동으로 UPDATE 쿼리가 실행됨
    }
    ```
*   **설명**: 먼저 권한을 확인한 후, 조회된 `post` 엔티티의 `complete` 메서드를 호출하여 내부 `status` 필드를 `Status.COMPLETED`로 변경합니다. 이 서비스 메서드는 `@Transactional`로 관리되고 있기 때문에, 메서드가 종료되는 시점에 JPA는 영속성 컨텍스트에 있는 `post` 엔티티의 상태가 변경되었음을 감지(더티 체킹)하고, 데이터베이스에 `UPDATE post SET status = 'COMPLETED' WHERE id = ?` 와 같은 SQL 쿼리를 자동으로 실행하여 변경사항을 반영합니다.

### 추가 기능 리뷰: 권한에 따른 UI 제어

### 6-1. 다른 사용자 게시글 조회 시 기능 비활성화

#### 6-1-1. 사용자 시나리오
사용자가 자신이 작성하지 않은 다른 사람의 게시글을 상세 조회했을 때, 게시글의 모든 내용은 볼 수 있지만, '수정', '삭제', '찾았어요!'와 같은 게시글 관리 버튼들은 화면에 보이지 않습니다.

*( 여기에 다른 사용자 게시글 상세 조회 시 버튼이 보이지 않는 화면 캡처 이미지 삽입 )*

#### 6-1-2. 코드 리뷰

**[Frontend] 작성자 여부 판별 및 조건부 렌더링**

*   **파일**: `src/pages/post/PostDetailPage.jsx`
*   **역할**: 전역 상태 관리(Context)를 통해 현재 로그인한 사용자의 정보를 가져오고, 이를 API로부터 받은 게시글 작성자 정보와 비교하여 UI(버튼)의 노출 여부를 동적으로 결정합니다.
*   **코드**:
    ```javascript
    // src/pages/post/PostDetailPage.jsx
    import { useAuth } from '../../context/AuthContext'; // 1. AuthContext 훅 import

    const PostDetailPage = () => {
        // ... 생략 ...
        const { user, isLoggedIn } = useAuth(); // 2. 로그인된 사용자 정보(user)와 로그인 상태(isLoggedIn) 가져오기
        const [post, setPost] = useState(null);

        // API 호출 후 post 상태에 게시글 정보 저장 (생략)
        
        // 3. 현재 로그인한 사용자가 게시글 작성자인지 판별
        //  - isLoggedIn이 true이고,
        //  - user 객체의 userId와 post 객체의 작성자(author) userId가 일치하는지 확인
        const isAuthor = isLoggedIn && user?.userId === post?.author.userId;

        return (
            <section className="board-section">
                <div className="post-detail">
                    {/* ... 게시글 헤더 및 내용 ... */}

                    {/* 4. isAuthor 변수가 true일 때만 이 블록 안의 버튼들을 렌더링 */}
                    {isAuthor && (
                        <div className="post-actions">
                            <Link to={`/posts/${postId}/edit`} className="btn btn-outline">수정</Link>
                            <button onClick={handleDelete} className="btn btn-danger">삭제</button>
                            <button onClick={handleComplete} className="btn btn-success">찾았어요!</button>
                        </div>
                    )}

                    {/* ... 이하 생략 ... */}
                </div>
            </section>
        );
    };
    ```
*   **설명**:
    1.  `useAuth` 훅을 호출하여 `AuthContext`에 저장된 현재 로그인된 사용자의 정보(`user`)를 가져옵니다. 이 `user` 객체에는 `userId`가 포함되어 있습니다.
    2.  `useEffect`를 통해 백엔드로부터 게시글 상세 정보를 조회하면, 응답 데이터(`post`) 안에는 작성자 정보(`author`)가 포함되어 있으며, 여기에도 `userId`가 있습니다.
    3.  `isAuthor` 라는 변수를 선언하여, `로그인된 사용자의 userId`와 `게시글 작성자의 userId`가 일치하는지 비교합니다. 두 ID가 일치하면 `isAuthor`는 `true`가 됩니다.
    4.  JSX 렌더링 부분에서 `isAuthor && (` 와 같은 **조건부 렌더링** 구문을 사용합니다. 이 구문은 `isAuthor`가 `true`일 경우에만 `&&` 뒤따라오는 `<div>` 블록(수정/삭제/완료 버튼 포함)을 화면에 그리고, `false`일 경우에는 아무것도 그리지 않아 자연스럽게 버튼이 비활성화(숨김 처리)됩니다.

**[Backend] 서버 단에서의 권한 검증 (예방적 방어)**

*   **파일**: `src/main/java/com/busanit501/findmyfet/service/post/PostServiceImpl.java`
*   **역할**: 프론트엔드에서 버튼이 보이지 않더라도, 누군가 악의적으로 API를 직접 호출하는 경우를 대비하여 서버 단에서 한 번 더 권한을 검증합니다. 게시글을 수정/삭제하려는 사용자가 실제 작성자나 관리자가 아닐 경우, 작업을 거부하고 예외를 발생시킵니다.
*   **코드**:
    ```java
    // src/main/java/com/busanit501/findmyfet/service/post/PostServiceImpl.java
    
    // 수정, 삭제, 완료 처리 메서드 내부에서 공통으로 사용되는 권한 검증 메서드
    private void validatePostAuthorOrAdmin(Post post, Long userId) {
        User user = userRepository.findById(userId)
                .orElseThrow(() -> new IllegalArgumentException("해당 사용자를 찾을 수 없습니다. id=" + userId));

        // ✅ 현재 요청한 사용자(userId)가 게시글 작성자(post.getUser().getUserId())도 아니고,
        //    관리자(Role.ADMIN)도 아니면 예외를 발생시킴
        if (!post.getUser().getUserId().equals(userId) && user.getRole() != Role.ADMIN) {
            throw new AccessDeniedException("해당 게시글에 대한 수정/삭제 권한이 없습니다.");
        }
    }

    // 예시: 게시글 삭제 서비스 메서드
    @Override
    @Transactional
    public void deletePost(Long postId,  Long userId) {
        Post post = postRepository.findById(postId).orElseThrow(/* ... */);
        
        // ✅ 실제 삭제 로직을 실행하기 전에 권한 검증 메서드를 반드시 호출
        validatePostAuthorOrAdmin(post, userId);

        // (권한이 확인된 후에만 아래 로직 실행)
        // ... 이미지 파일 삭제 및 게시글 삭제 로직 ...
    }
    ```
*   **설명**: 프론트엔드의 UI 제어는 사용자 편의를 위한 것이며, 실제 보안은 백엔드에서 책임져야 합니다. `deletePost`, `updatePost`, `completePost`와 같이 중요한 데이터를 변경하는 모든 서비스 메서드 시작 부분에서 `validatePostAuthorOrAdmin`이라는 공통 검증 메서드를 호출합니다. 이 메서드는 DB에서 조회한 `Post` 엔티티의 작성자 ID와 JWT 토큰으로부터 추출한 현재 사용자의 ID를 비교합니다. 만약 두 ID가 다르고 사용자가 관리자도 아니라면, `AccessDeniedException` 예외를 발생시켜 작업을 즉시 중단시키고 클라이언트에 403 Forbidden 과 같은 에러를 응답합니다.

### 9-1. '찾기 완료' 게시글의 기능 비활성화

#### 9-1-1. 사용자 시나리오
'찾았어요!' 처리가 완료된 게시글의 상세 페이지에 다시 접속하면, 이전에 보였던 '수정', '삭제', '찾았어요!' 버튼들이 모두 사라진 것을 확인할 수 있습니다. 완료된 게시글은 더 이상 수정하거나 삭제할 수 없습니다.

*( 여기에 '찾았어요!' 상태 뱃지와 함께, 하단에 관리 버튼이 보이지 않는 상세 페이지 캡처 이미지 삽입 )*

#### 9-1-2. 코드 리뷰

**[Frontend] '완료' 상태에 따른 조건부 렌더링**

*   **파일**: `src/pages/post/PostDetailPage.jsx`
*   **역할**: API로부터 받은 게시글의 `status` 값을 확인하여, 'COMPLETED' 상태일 경우 관리 버튼들을 렌더링하지 않도록 제어합니다.
*   **코드**:
    ```javascript
    // src/pages/post/PostDetailPage.jsx
    
    const PostDetailPage = () => {
        // ... isAuthor 변수 선언까지는 위와 동일 ...
        const isAuthor = isLoggedIn && user?.userId === post?.author.userId;

        // ✅ 1. API 응답 데이터(post)의 status가 'COMPLETED'인지 확인하는 변수
        const isCompleted = post?.status === 'COMPLETED';

        return (
            <section className="board-section">
                <div className="post-detail">
                    <div className="post-detail-header">
                        {/* status 값에 따라 '찾는 중' 또는 '찾았어요!' 뱃지를 동적으로 표시 */}
                        <div className={`status-badge ${isCompleted ? 'status-completed' : 'status-active'}`}>
                            {isCompleted ? '찾았어요!' : '찾는 중'}
                        </div>
                        {/* ... 게시글 제목 및 정보 ... */}
                    </div>
                    
                    {/* ✅ 2. '작성자'이면서 '완료되지 않은' 게시글일 때만 버튼을 렌더링 */}
                    {isAuthor && !isCompleted && (
                        <div className="post-actions">
                            <Link to={`/posts/${postId}/edit`} className="btn btn-outline">수정</Link>
                            <button onClick={handleDelete} className="btn btn-danger">삭제</button>
                            <button onClick={handleComplete} className="btn btn-success">찾았어요!</button>
                        </div>
                    )}
                    
                    {/* ... 이하 생략 ... */}
                </div>
            </section>
        );
    };
    ```
*   **설명**:
    1.  `isCompleted` 라는 변수를 선언하여, 백엔드로부터 받은 `post` 객체의 `status` 값이 `'COMPLETED'`와 일치하는지 확인합니다.
    2.  버튼들을 렌더링하는 조건부 렌더링 구문을 `isAuthor && !isCompleted && (` 로 수정합니다. 이 구문은 **'현재 사용자가 작성자'이면서(isAuthor) 동시에 '게시글이 아직 완료되지 않았을 때(!isCompleted)'** 라는 두 가지 조건을 모두 만족해야만 `true`가 됩니다.
    3.  따라서 '찾기 완료' 처리가 된 게시글은 `isCompleted`가 `true`가 되므로 조건이 `false`로 평가되어, 작성자 본인이 접속하더라도 수정/삭제/완료 버튼이 더 이상 화면에 나타나지 않습니다.
